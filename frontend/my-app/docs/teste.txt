2) Análise da rota forgot-password

As rotas já existem e estão corretamente estruturadas no App Router do Next.js:
- /forgot-password
- /forgot-password/reset-password

Estrutura:
- src/app/(auth)/forgot-password/page.tsx
- src/app/(auth)/forgot-password/reset-password/page.tsx

Isso está correto porque o route group (auth) não aparece na URL; ele serve apenas para organizar as rotas.

O problema não é a rota em si, e sim a lógica dentro dela.

No código atual, o fluxo da recuperação está simulado:
- no forgot-password, o email é comparado a uma string fixa
- se bater, o sistema navega para a página de reset
- no reset password, só compara a senha e confirmação
- depois redireciona para /login

Isso não é um sistema real de recuperação de senha.

3) Como normalmente funciona o forgot password

O fluxo real é:
1. Usuário coloca o email
2. Frontend valida o email
3. Backend verifica se o email existe
4. Backend gera um token seguro
5. Backend salva o token e sua expiração
6. Backend envia um link para o email
7. Usuário clica no link
8. Página de reset lê o token da URL
9. Usuário define nova senha
10. Backend valida o token e atualiza a senha
11. Redireciona para login

4) Explicação do email + token

Esse é o modelo comum para recuperação de senha.

Email = identificação do usuário
Token = prova de que a pessoa tem acesso ao email

Sem o token, um atacante que só saiba o email não consegue trocar a senha.

Fluxo com email + token:
- Usuário pede recuperação
- Backend procura usuário pelo email
- Gera token aleatório
- Salva token + expiração
- Envia link: /forgot-password/reset-password?token=abc123
- Usuário acede ao link
- Backend valida token
- Usuário define nova senha
- Backend atualiza senha e invalida o token

Isso é a segunda camada de segurança e o que normalmente é usado por sistemas como Google/Facebook.

6) Como normalmente a página de perfil deve funcionar

A lógica correta é:
1. Buscar os dados do usuário no backend
2. Preencher o formulário com esses dados
3. Usuário alterar campos
4. Submeter o formulário
5. Backend guardar os dados atualizados

Em React + react-hook-form:
- useForm cria o estado do formulário
- register liga cada input ao form
- handleSubmit valida e envia
- reset(...) preenche os dados vindos do backend

Exemplo de lógica:

useEffect(() => {
  async function loadUser() {
    const response = await fetch('/api/user/me');
    const user = await response.json();

    reset({
      name: user.name,
      email: user.email,
      phone: user.phone,
      gender: user.gender,
    });
  }

  loadUser();
}, [reset]);

E o submit seria algo como:

async function onSubmit(data) {
  await fetch('/api/user/me', {
    method: 'PUT',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(data),
  });
}

7) Sobre o onChange com hook form

Quando se usa react-hook-form, normalmente não se faz onChange manualmente para cada input.

Em vez disso, usa-se:

<input {...register('name')} />
<input {...register('email')} />
<select {...register('gender')} />

O register já faz:
- atualizar o valor do campo
- guardar no estado do form
- entregar os valores no submit

10) Como o edit-profile deve funcionar com o banco de dados (passo a passo)

A página de perfil deve funcionar assim:

Passo 1: buscar os dados do usuário autenticado
- Quando a página abre, o frontend faz um pedido ao backend para obter os dados do utilizador logado.
- Normalmente a rota é algo como: GET /api/user/me
- O backend usa o token da sessão para identificar quem está autenticado.

Exemplo:

fetch('/api/user/me', {
  headers: {
    Authorization: `Bearer ${token}`
  }
})

O backend responde:

{
  "id": 1,
  "name": "Ilda Nhanga",
  "email": "ilda@gmail.com",
  "phone": "923456789",
  "gender": "Feminino"
}

Passo 2: preencher o formulário com os dados do utilizador
- O frontend recebe o objeto do utilizador.
- Usa o reset() do react-hook-form para preencher os inputs.

Exemplo:

reset({
  name: user.name,
  email: user.email,
  phone: user.phone,
  gender: user.gender
})

Assim os inputs passam a mostrar exatamente o que está guardado no banco.

Passo 3: o utilizador altera os campos
- Cada input fica ligado ao react-hook-form com register.
- Quando o utilizador digita ou altera um campo, o hook guarda o valor automaticamente.

Exemplo:

<input {...register('name')} />
<input {...register('email')} />
<input {...register('phone')} />
<select {...register('gender')} />

No onChange não é preciso fazer manualmente, porque o register já trata isso.

Passo 4: validar os dados antes de enviar
- Antes de gravar, a aplicação valida:
- nome obrigatório
- email válido
- telefone com tamanho mínimo
- género obrigatório

Isso normalmente é feito com Zod e zodResolver.

Exemplo de schema:

const EditProfileSchema = z.object({
  name: z.string().min(2, 'Nome obrigatório'),
  email: z.string().email('Email inválido'),
  phone: z.string().min(9, 'Telefone inválido'),
  gender: z.enum(['Masculino', 'Feminino'])
});

Passo 5: enviar os dados para o backend
- Quando o utilizador clicar em Guardar, o frontend chama a API de atualização.
- Normalmente usa PUT ou PATCH.

Exemplo:

fetch('/api/user/me', {
  method: 'PUT',
  headers: {
    'Content-Type': 'application/json',
    Authorization: `Bearer ${token}`
  },
  body: JSON.stringify(data)
})

Passo 6: o backend atualiza o usuário
- O backend recebe os dados do formulário.
- Valida novamente.
- Busca o utilizador logado pelo token.
- Atualiza os campos no banco.

Exemplo de lógica no backend:

const user = await prisma.user.update({
  where: { id: userId },
  data: {
    name: data.name,
    email: data.email,
    phone: data.phone,
    gender: data.gender,
  }
});

Passo 7: responder sucesso ao frontend
- O backend responde com sucesso ou erro.
- O frontend mostra mensagem de confirmação.

Exemplo:

if (!response.ok) {
  alert('Erro ao atualizar perfil');
  return;
}

alert('Perfil atualizado com sucesso');

Passo 8: recarregar ou atualizar a UI
- Depois da atualização, o frontend pode:
- mostrar uma mensagem de sucesso
- atualizar o estado local
- ou recarregar os dados do utilizador

O importante é que a UI reflita o novo valor guardado no banco.

15) Aula: relations no Drizzle ORM

Uma relation descreve como duas tabelas se ligam. Exemplo:
- um utilizador pode fazer muitos pedidos de inscrição;
- cada pedido pertence a um único utilizador.

users (1) ---------------- (N) membership_requests

Como descobrir onde criar uma relation:
- "Este registo pertence a quem?" indica uma relation one.
- "Este registo pode ter vários filhos?" indica uma relation many.
- A tabela pai possui uma primary key.
- A tabela filha guarda a foreign key.

Não cries uma relation apenas porque duas tabelas têm campos parecidos. Cria-a
quando existe uma regra real de pertencimento ou associação.

Primeiro, cria a foreign key na tabela do lado many:

import { integer, pgTable, serial, text } from 'drizzle-orm/pg-core';

export const users = pgTable('users', {
  id: serial('id').primaryKey(),
  name: text('name').notNull(),
});

export const membershipRequests = pgTable('membership_requests', {
  id: serial('id').primaryKey(),
  userId: integer('user_id')
    .notNull()
    .references(() => users.id),
  status: text('status').notNull(),
});

O references() cria a foreign key real no banco. Sem ele, userId é apenas um
número e o banco não garante que o utilizador exista.

Depois, declara as relations do Drizzle:

import { relations } from 'drizzle-orm';

export const usersRelations = relations(users, ({ many }) => ({
  membershipRequests: many(membershipRequests),
}));

export const membershipRequestsRelations = relations(
  membershipRequests,
  ({ one }) => ({
    user: one(users, {
      fields: [membershipRequests.userId],
      references: [users.id],
    }),
  }),
);

Diferença importante:
- references() cria a ligação no banco;
- relations() ensina o Drizzle a navegar entre os dados;
- normalmente precisas dos dois.

Tipos principais:

one:
Um pedido pertence a um utilizador:

user: one(users, {
  fields: [membershipRequests.userId],
  references: [users.id],
})

many:
Um utilizador possui muitos pedidos:

membershipRequests: many(membershipRequests)

many-to-many:
Quando muitos utilizadores podem participar em muitos jogos, cria uma tabela
intermediária:

users -------- match_players -------- matches

match_players guarda userId e matchId. Cada coluna possui uma foreign key.

Para consultar dados relacionados, usa with:

const result = await db.query.users.findMany({
  with: {
    membershipRequests: true,
  },
});

Para consultar o pedido e o seu utilizador:

const result = await db.query.membershipRequests.findMany({
  with: {
    user: true,
  },
});

Usa with para carregar relações de forma simples. Usa innerJoin ou leftJoin
quando precisares de filtros, agregações ou uma consulta SQL mais específica.

const result = await db
  .select()
  .from(membershipRequests)
  .innerJoin(users, eq(membershipRequests.userId, users.id));

Depois de alterar as tabelas:
1) altera o schema;
2) gera a migration;
3) aplica a migration no banco;
4) testa insert, update e select com with.

Com drizzle-kit, os comandos costumam ser:

pnpm drizzle-kit generate
pnpm drizzle-kit migrate

Erros comuns:
- criar relations sem foreign key;
- inverter fields e references;
- esquecer a relation inversa;
- usar many quando a regra é one;
- guardar vários ids numa string em vez de criar tabela intermediária;
- alterar o schema sem gerar ou aplicar migration;
- consultar db.query sem configurar o schema no db.

Regra para fields e references:
- fields é a coluna da tabela atual que guarda o id relacionado;
- references é a coluna primary key ou unique da tabela referenciada.

Método prático:
a) desenha as tabelas e pergunta quem pertence a quem;
b) define a primary key de cada tabela;
c) coloca a foreign key no lado many;
d) adiciona references();
e) adiciona relations() nos dois lados;
f) gera e aplica a migration;
g) testa a leitura com with e a escrita com insert.

17) Perguntas frequentes de entrevista

Por que escolheste Next.js?
Resposta possível: escolhi Next.js porque ele fornece uma estrutura para React
com routing, layouts, otimização e possibilidade de usar server-side rendering.

Por que usaste React Hook Form?
Resposta possível: para controlar formulários com menos código e integrar a
validação do Zod através do resolver.

Para que serve o Zod?
Resposta possível: define um schema executável que valida os dados em runtime
e também permite gerar tipos TypeScript com z.infer.

Qual a diferença entre optional e nullable?
optional aceita undefined ou campo ausente. nullable aceita null. Nenhum dos
dois aceita automaticamente uma string vazia quando há outras validações.

Como protegerias uma rota?
Usaria autenticação no backend, verificaria a sessão antes de responder e
aplicaria autorização para confirmar o papel do utilizador.

Como tratarias uma falha da API?
Mostraria um estado de erro, manteria os dados preenchidos, permitiria tentar
novamente e registaria detalhes técnicos apenas no local apropriado.

Como relacionarias utilizadores e partidas?
Se um utilizador puder participar em várias partidas e uma partida tiver vários
utilizadores, criaria users, matches e uma tabela intermediária match_players.

O que farias se um componente ficasse grande?
Separaria partes reutilizáveis, moveria regras para hooks ou funções próprias e
manteria o componente responsável apenas pela composição da interface.

Como testarias o EditProfile?
Testaria renderização, preenchimento, validação de email, seleção de género,
upload válido, upload inválido, submit válido, erro da API e cancelamento.

25) Aula: JWT, Argon2 e refresh tokens com Fastify

Objetivo:
Criar um sistema de autenticação em que:
- a password nunca é guardada diretamente;
- o access token expira rapidamente;
- o refresh token permite obter um novo access token;
- o refresh token pode ser revogado no logout;
- o backend valida tudo antes de autorizar o utilizador.

1. Conceitos fundamentais

Autenticação responde:
"Quem é este utilizador?"

Autorização responde:
"Este utilizador pode executar esta ação?"

JWT significa JSON Web Token. É um token assinado que normalmente contém:
- sub: id do utilizador;
- role: papel do utilizador;
- jti: identificador único do token;
- iat: momento de criação;
- exp: momento de expiração.

O JWT tem três partes separadas por pontos:

header.payload.signature

O payload não é secreto. É apenas codificado em Base64URL. Nunca coloques
passwords, segredos ou dados sensíveis dentro do payload.

2. Access token e refresh token

Access token:
- usado para aceder às rotas protegidas;
- vida curta, por exemplo 15 minutos;
- enviado no header Authorization;
- se for roubado, a janela de uso é limitada.

Exemplo de header:

Authorization: Bearer ACCESS_TOKEN

Refresh token:
- usado apenas para pedir um novo access token;
- vida mais longa, por exemplo 7 dias;
- deve ficar num cookie HttpOnly;
- deve poder ser revogado;
- não deve ser usado para acessar qualquer rota da aplicação.

Fluxo:

1) login com email e password;
2) backend verifica a password com Argon2;
3) backend cria access token curto;
4) backend cria refresh token longo;
5) backend guarda no banco o id ou hash da sessão;
6) backend envia o refresh token em cookie HttpOnly;
7) frontend usa o access token nas requisições;
8) quando o access token expira, chama POST /auth/refresh;
9) backend valida e roda o refresh token;
10) backend envia novos tokens.

3. Instalação no Fastify

Instala os pacotes:

pnpm add fastify @fastify/jwt @fastify/cookie argon2
pnpm add -D @types/node typescript

Se usares TypeScript, também deves configurar o tsconfig e os scripts de
desenvolvimento do backend.

4. Variáveis de ambiente

Nunca escrevas secrets diretamente no código.

Exemplo de .env:

JWT_ACCESS_SECRET=uma-chave-longa-e-aleatoria-para-access
JWT_REFRESH_SECRET=outra-chave-longa-e-aleatoria-para-refresh
NODE_ENV=development

Em produção:
- usa secrets diferentes;
- usa valores longos e aleatórios;
- não envies o .env para o Git;
- configura os secrets no serviço de deploy.

5. Configurar JWT no Fastify

import Fastify from 'fastify';
import fastifyJwt from '@fastify/jwt';
import fastifyCookie from '@fastify/cookie';

const app = Fastify({ logger: true });

await app.register(fastifyCookie);

await app.register(fastifyJwt, {
  secret: process.env.JWT_ACCESS_SECRET!,
});

O plugin fornece sign() para criar tokens e jwtVerify() para verificar tokens.

Para access e refresh tokens com secrets diferentes, uma opção clara é usar
duas instâncias ou assinar o refresh token diretamente com jsonwebtoken. Outra
opção é usar o mesmo plugin com uma estratégia definida para distinguir os
tipos. O importante é não aceitar um refresh token como access token.

Uma abordagem simples para começar é usar o mesmo segredo, incluir type no
payload e verificar esse type em cada rota. Para maior isolamento, usa secrets
separados e uma função própria para assinar/verificar refresh tokens.

6. Hash da password com Argon2

Nunca guardes isto:

password: '12345678'

Guarda apenas o hash:

import argon2 from 'argon2';

const passwordHash = await argon2.hash(password);

No login:

const passwordIsValid = await argon2.verify(
  user.passwordHash,
  password,
);

if (!passwordIsValid) {
  return reply.code(401).send({
    message: 'Credenciais inválidas',
  });
}

Não precisas guardar o salt separadamente. O Argon2 inclui no hash as
informações necessárias para fazer a verificação.

7. Tabela de sessões ou refresh tokens

Não é suficiente criar um refresh token e nunca o guardar. Sem persistência,
fica difícil revogar uma sessão específica.

Exemplo de tabela conceptual:

refresh_sessions:
- id;
- user_id;
- token_hash;
- expires_at;
- revoked_at;
- replaced_by;
- created_at;

Guarda o hash do refresh token, e não necessariamente o token original:

const refreshTokenHash = await argon2.hash(refreshToken);

No momento da renovação, procuras a sessão do utilizador e verificas:

await argon2.verify(session.tokenHash, refreshToken);

Também podes usar um hash SHA-256 para procurar rapidamente pelo token e
depois aplicar uma verificação adicional. O princípio é não guardar tokens
de sessão em texto puro sem necessidade.

8. Criar os tokens no login

Payload mínimo recomendado:

type AuthPayload = {
  sub: string;
  role: 'user' | 'admin';
  type: 'access' | 'refresh';
  jti: string;
};

Exemplo conceitual:

const accessToken = await app.jwt.sign(
  {
    sub: String(user.id),
    role: user.role,
    type: 'access',
    jti: crypto.randomUUID(),
  },
  { expiresIn: '15m' },
);

O refresh token deve ter outro jti e expiração maior. Guarda no banco a sessão
associada a esse jti ou ao hash do token.

9. Rota de login

POST /auth/login

Passos da rota:
1) validar email e password;
2) procurar o utilizador pelo email;
3) verificar passwordHash com argon2.verify;
4) responder 401 se falhar;
5) criar access token;
6) criar refresh token;
7) guardar a sessão do refresh token;
8) enviar refresh token em cookie;
9) devolver access token e dados públicos do utilizador.

Exemplo de resposta:

{
  "accessToken": "eyJ...",
  "user": {
    "id": 1,
    "name": "Ilda Nhanga",
    "role": "user"
  }
}

Nunca devolvas passwordHash na resposta.

10. Cookie do refresh token

Exemplo:

reply.setCookie('refresh_token', refreshToken, {
  httpOnly: true,
  secure: process.env.NODE_ENV === 'production',
  sameSite: 'strict',
  path: '/auth',
  maxAge: 60 * 60 * 24 * 7,
});

Significado:
- httpOnly impede JavaScript do browser de ler o cookie;
- secure envia o cookie apenas por HTTPS em produção;
- sameSite reduz riscos de CSRF;
- path limita onde o cookie será enviado;
- maxAge define a duração do cookie.

Se o frontend e backend estiverem em domínios diferentes, configura CORS com
credentials e usa sameSite conforme a arquitetura. Não uses allowOrigin '*'
junto com credentials: true.

11. Hook de autenticação para rotas protegidas

Cria uma função que verifica o access token:

async function authenticate(request: FastifyRequest, reply: FastifyReply) {
  try {
    await request.jwtVerify();
  } catch {
    return reply.code(401).send({
      message: 'Não autenticado',
    });
  }
}

Usa-a numa rota:

app.get('/users/me', { onRequest: authenticate }, async (request) => {
  const userId = request.user.sub;

  return getUserById(userId);
});

O id deve vir do token verificado, não de um id enviado livremente pelo cliente.

12. Verificar role e autorização

Autenticar não significa autorizar.

Exemplo:

async function onlyAdmin(request: FastifyRequest, reply: FastifyReply) {
  await authenticate(request, reply);

  if (reply.sent) return;

  if (request.user.role !== 'admin') {
    return reply.code(403).send({
      message: 'Sem permissão',
    });
  }
}

Usa 401 quando não existe autenticação válida. Usa 403 quando a identidade é
conhecida, mas não possui permissão para a ação.

13. Rota de refresh

POST /auth/refresh

Passos:
1) ler o cookie refresh_token;
2) responder 401 se não existir;
3) verificar assinatura, type, jti e expiração;
4) procurar a sessão no banco;
5) rejeitar sessão revogada ou expirada;
6) verificar o hash do token;
7) revogar o refresh token antigo;
8) criar um novo access token;
9) criar um novo refresh token;
10) guardar a nova sessão;
11) substituir o cookie.

Isto chama-se refresh token rotation. O token antigo deixa de ser válido depois
de usado. Se um token antigo for usado novamente, pode indicar roubo; nesse
caso, revoga toda a família de sessões relacionada.

14. Rota de logout

POST /auth/logout

Passos:
1) ler o refresh token do cookie;
2) localizar a sessão;
3) marcar revoked_at;
4) limpar o cookie;
5) responder 204 ou 200.

Exemplo:

await revokeRefreshSession(refreshToken);

reply.clearCookie('refresh_token', {
  httpOnly: true,
  secure: process.env.NODE_ENV === 'production',
  sameSite: 'strict',
  path: '/auth',
});

return reply.code(204).send();

15. Refresh token não é password

Argon2 é usado principalmente para passwords porque é lento de propósito e
resiste melhor a ataques offline.

JWT é usado para transportar uma identidade assinada.

Refresh token é uma credencial de sessão e deve ser tratado como segredo:
- não mostrar nos logs;
- não colocar em localStorage quando puderes usar cookie HttpOnly;
- revogar no logout;
- expirar;
- rodar após cada utilização;
- armazenar de forma controlada.

16. Frontend usando access e refresh

No login:
1) frontend envia email e password;
2) browser recebe o cookie automaticamente;
3) frontend guarda o access token apenas enquanto necessário;
4) frontend envia Authorization nas chamadas protegidas.

Quando recebe 401 por expiração:
1) chama POST /auth/refresh com credentials;
2) recebe novo access token;
3) repete a requisição original uma vez;
4) se falhar novamente, leva o utilizador para login.

Com fetch:

fetch('/auth/refresh', {
  method: 'POST',
  credentials: 'include',
});

O frontend não precisa ler o refresh token. O browser envia o cookie HttpOnly.

17. Proteções obrigatórias

- usa HTTPS em produção;
- usa secrets fortes;
- define expiração para os tokens;
- valida o payload recebido;
- rejeita token com type errado;
- revoga refresh tokens;
- aplica rate limit em login e refresh;
- usa mensagens genéricas para credenciais inválidas;
- não revela se um email existe no forgot password;
- não imprime tokens nos logs;
- não guarda password em texto puro;
- não confia no role enviado pelo frontend;
- valida autorização em todas as rotas sensíveis;
- protege cookies contra CSRF conforme a arquitetura;
- atualiza dependências.

18. Erros comuns

- guardar password diretamente na tabela;
- usar o access token como refresh token;
- guardar refresh token no localStorage sem necessidade;
- nunca revogar sessões;
- usar o mesmo segredo exposto no repositório;
- colocar dados sensíveis no JWT;
- aceitar qualquer token sem verificar type;
- confiar apenas no middleware do frontend;
- esquecer credentials no CORS;
- usar cookie secure em HTTP local e pensar que o login falhou;
- não tratar expiração;
- criar refresh infinito sem rotação;
- devolver passwordHash ao cliente;
- responder detalhes diferentes para email inexistente e password errada.

19. Ordem recomendada de implementação

1) criar tabela users;
2) criar schema de cadastro;
3) criar hash de password com Argon2;
4) criar POST /auth/register;
5) criar POST /auth/login;
6) configurar JWT;
7) criar tabela de sessões;
8) criar cookie de refresh;
9) criar POST /auth/refresh;
10) criar POST /auth/logout;
11) criar authenticate;
12) proteger GET /users/me;
13) criar autorização por role;
14) adicionar rate limit;
15) testar login, refresh, logout, expiração e revogação.

20. Checklist de teste

- cadastro com password válida;
- cadastro com email repetido;
- login com credenciais corretas;
- login com password errada;
- login com utilizador inexistente;
- acesso sem access token;
- acesso com access token expirado;
- refresh com cookie válido;
- refresh sem cookie;
- refresh com cookie revogado;
- reutilização do refresh token antigo;
- logout;
- acesso de user a rota admin;
- acesso de admin a rota admin;
- password nunca aparece nos logs;
- tokens nunca aparecem nos logs;
- cookie possui HttpOnly, Secure e SameSite corretos.

21. Resumo final

Argon2 protege a password.
JWT access token identifica o utilizador por pouco tempo.
Refresh token mantém a sessão por mais tempo.
Fastify organiza as rotas, hooks e plugins.
O banco guarda as sessões para permitir revogação.

Fluxo seguro:

password --Argon2--> passwordHash
login --> access token curto + refresh token em cookie
request protegida --> valida access token
access expirado --> refresh rotation
logout --> revoga sessão + limpa cookie

O objetivo não é apenas fazer o login funcionar. É garantir que uma sessão
pode expirar, ser renovada, ser revogada e ser autorizada corretamente.
